# Botamin Call Growth Dashboard

Рабочий аналитический дашборд для анализа звонков голосового AI-бота продаж.

Продукт загружает Excel-выгрузку звонков, строит воронку, находит основную точку потери клиентов, отделяет технические проблемы от проблем скрипта и предлагает первый A/B-тест.

Проект создан как тестовое задание на позицию Product Owner AI-продукта в B2B Salestech.

---

## Что решает продукт

Аналитик Botamin работает с тысячами звонков голосового бота.

Сырая Excel-выгрузка не позволяет быстро понять:

* сколько звонков дошло до содержательного разговора;
* сколько звонков потеряно из-за технических проблем;
* на каком этапе бот чаще всего теряет клиента;
* доходит ли разговор до оффера;
* получает ли бот сигнал релевантности;
* предлагает ли следующий шаг;
* соглашается ли клиент;
* какие звонки необходимо проверить вручную;
* какой A/B-тест стоит запустить первым.

Botamin Call Growth Dashboard превращает сырые данные в продуктовую диагностику:

```text
Excel
→ валидация
→ нормализация
→ классификация звонков
→ техническая диагностика
→ воронка
→ drop-off
→ главная точка роста
→ первый A/B-тест
→ аналитические вопросы
→ CSV-экспорт
```

## Основные возможности

Приложение поддерживает два режима:

1. Автоматическая загрузка файла:

### Валидация Excel

Приложение проверяет:

* наличие обязательных колонок;
* корректность чтения Excel;
* наличие строк;
* формат длительности;
* наличие колонки с транскриптом.

Обязательные колонки:

```text

длительность мин:сек
статус
запись аудио
причина завершения
история диалога юзер-бот
```

При ошибках приложение показывает понятное сообщение и не выводит пользователю необработанный traceback.

## Воронка звонка

Каждый звонок классифицируется по максимальному достигнутому этапу.

```text
0_no_dialog
1_contact_greeting
2_consent_permission
3_offer_delivered
4_relevance_signal_detected
5_next_step_proposed
6_next_step_accepted
7_context_collected_or_correctly_finished
```

### 0 — No Dialog

Нет содержательного диалога:

* транскрипт отсутствует;
* транскрипт пустой;
* звонок завершился до содержательного контакта.

### 1 — Contact / Greeting

Бот или клиент установили первичный контакт.

### 2 — Consent / Permission

Бот получил или попытался получить разрешение на короткий разговор.

### 3 — Offer Delivered

Бот донёс оффер и объяснил ценность продукта.

### 4 — Relevance Signal Detected

В разговоре появился проверяемый сигнал потенциальной релевантности клиента.

Например:

* есть отдел продаж;
* есть база клиентов;
* есть заявки;
* используется CRM;
* клиент является ЛПР;
* клиент задаёт содержательный вопрос;
* клиент проявляет реальный интерес.

Простые реакции вроде «да», «угу», «понятно» сами по себе не считаются сигналом релевантности.

### 5 — Next Step Proposed

Бот предложил осмысленное продолжение:

* встречу;
* демо;
* звонок эксперта;
* отправку материалов;
* перезвон;
* передачу контакта ЛПР.

### 6 — Next Step Accepted

Клиент явно или косвенно согласился на следующий шаг.

Попытка бота назначить встречу не считается успехом без согласия клиента.

### 7 — Context Collected / Correctly Finished

Диалог завершён осмысленно:

* согласована встреча;
* согласован звонок эксперта;
* клиент запросил материалы;
* договорились о перезвоне;
* передан контакт ЛПР;
* собран полезный контекст;
* нерелевантный клиент корректно завершён.

## Техническая диагностика звонков без текста

Звонок без транскрипта не всегда означает, что клиент сразу сбросил.

Приложение разделяет такие звонки на несколько типов.

### Early No-dialog

Очень короткий звонок без текста.

Например:

```text
duration_seconds <= 10
```

Вероятная интерпретация: ранний сброс до начала разговора.

### Suspicious No-transcript

Звонок длился заметное время, но транскрипт отсутствует.

Например:

```text
duration_seconds >= 30
```

Это может указывать на:

* проблему транскрибации;
* проблему сохранения текста;
* ошибку логирования;
* проблему аудиозаписи;
* некорректное завершение звонка.

### Fixed Timeout Without Transcript

Пустой транскрипт при фиксированной длительности:

```text
180 секунд
240 секунд
```

Это рассматривается как возможная системная аномалия.

### Bot Hangup Without Transcript

Бот завершил звонок, но текст разговора отсутствует:

```text
termination_reason = bot_hangup
```

Такие звонки показываются отдельно в разделе технической диагностики.

## Главная метрика

Основная продуктовая метрика:

```text
Qualified Next Step Rate
```

Формула:

```text
звонки, где:
has_relevance_signal = true
и next_step_proposed = true
и next_step_accepted = true

делённые на общее количество звонков
```

Дополнительно рассчитывается:

```text
Qualified Next Step Rate From Conversations
```

Формула:

```text
qualified next step calls / calls with transcript
```

### Почему не Meeting Rate

Простое количество встреч может быть ложной метрикой.

Бот может назначать встречи нерелевантным клиентам и создавать лишнюю нагрузку на менеджеров.

Qualified Next Step Rate показывает не просто факт назначения встречи, а осмысленное продолжение с потенциально релевантным клиентом.

---

## Адаптивный главный экран

Главный экран не показывает все метрики одновременно.

Постоянно отображаются:

* Total Calls;
* Calls With Transcript;
* Calls Without Transcript / No Transcript Rate.

Остальные карточки меняются в зависимости от найденной главной проблемы.

Если проблема техническая, показываются:

* Suspicious No-transcript Calls;
* Fixed Timeout Without Transcript;
* Bot Hangup Without Transcript.

Если проблема связана с оффером, показываются:

* Offer Reach Rate;
* Offer → Relevance Signal Conversion;
* Relevance Signal Rate.

Если проблема связана со следующим шагом, показываются:

* Next Step Proposal Rate;
* Next Step Acceptance Rate;
* Proposal → Acceptance Conversion.

Это позволяет аналитику сразу видеть не все возможные показатели, а только цифры, которые подтверждают текущую гипотезу.

## Main Growth Opportunity

Приложение автоматически определяет главную точку роста.

Приоритет анализа:

1. Suspicious No-transcript / Technical Loss.
2. Contact → Consent.
3. Consent → Offer.
4. Offer → Relevance Signal.
5. Relevance → Next Step Proposed.
6. Proposal → Acceptance.
7. Acceptance → Context / Finish.
8. Meeting Without Relevance Signal.

Рекомендация содержит:

* основную проблему;
* объяснение, почему она важна;
* подтверждающую метрику;
* затронутый этап воронки;
* рекомендуемый фокус работы.

Технические проблемы имеют приоритет над оптимизацией скрипта, если значительная часть звонков не содержит транскрипта при заметной длительности или фиксированном таймауте.

## Первый A/B-тест

На основе главной точки роста приложение автоматически формирует первый тест.

Блок содержит:

* гипотезу;
* Variant A;
* Variant B;
* основную метрику;
* guardrail-метрики;
* ожидаемый эффект.

Пример для проблемы Offer → Relevance Signal:

```text
Variant B:

Мы запускаем AI-продавца в первую линию:
он сам прозванивает базу, задаёт первые вопросы
и передаёт менеджерам только потенциально релевантных клиентов.

Подскажите, у вас сейчас есть база или заявки,
которые менеджеры регулярно обзванивают?
```

Основная метрика:

```text
Offer → Relevance Signal Conversion
```

## Ask the Dashboard

Раздел позволяет задавать вопросы по уже рассчитанным данным.

Это не универсальный чатбот.

Он работает через локальную intent-based логику и отвечает на основе:

* рассчитанных метрик;
* воронки;
* drop-off;
* обработанного DataFrame;
* найденной рекомендации;
* подготовленного A/B-теста.

Примеры вопросов:

```text
Где самый большой drop-off?
Почему Qualified Next Step Rate низкий?
Сколько звонков без текста?
Сколько подозрительных звонков без транскрипта?
Есть ли длинные звонки без текста?
Покажи примеры звонков без relevance signal.
Какой A/B-тест запустить первым?
Почему выбрана эта гипотеза?
```

Поддерживаются короткие уточняющие вопросы:

```text
покажи примеры
почему
что делать
какой тест
сколько таких
покажи подробнее
```

Контекст текущей сессии хранится через `st.session_state`.

### Важно

Ask the Dashboard не использует Gemma.

Он работает без AI-модели и без внешнего API.

## Local Gemma Helper

Локальная Gemma используется опционально для улучшения уже сформированной гипотезы и A/B-теста.

Gemma не используется для:

* массовой обработки всех звонков;
* построения воронки;
* расчёта метрик;
* обязательной работы приложения.

Она включается только по кнопке пользователя.

В Gemma передаётся компактный аналитический контекст:

* главная проблема;
* supporting metrics;
* weakest funnel stage;
* текущая гипотеза;
* текущий A/B-тест;
* несколько примеров звонков.

Gemma помогает:

* уточнить формулировку гипотезы;
* улучшить Variant B;
* объяснить выбор теста;
* предложить guardrail-метрики;
* сформировать рекомендацию для ручной проверки.

Используемая модель:

```text
gemma4:e2b
```

Провайдер:

```text
Ollama
```

---

## Настройка Gemma

Создайте файл `.env` в корне проекта:

```env
ENABLE_LOCAL_AI=true
LOCAL_LLM_PROVIDER=ollama
LOCAL_LLM_BASE_URL=http://localhost:11434
LOCAL_LLM_MODEL=gemma4:e2b
LOCAL_LLM_TIMEOUT_SECONDS=120
```

Проверьте наличие модели:

```powershell
ollama list
```

Запуск модели:

```powershell
ollama run gemma4:e2b
```

Если Ollama или модель недоступны, основной дашборд продолжает работать.

В production локальный AI-слой можно заменить на:

* OpenAI API;
* Gemini API;
* Claude API;
* другую LLM.

Основная аналитическая логика продукта от этого не зависит.

## Логирование

Приложение использует стандартный модуль Python `logging`.

Логи выводятся:

* в терминал;
* в файл:

```text
logs/app.log
```

Логируются:

* запуск приложения;
* загрузка Excel;
* имя источника данных;
* количество строк;
* ошибки валидации;
* предупреждения парсинга длительности;
* завершение предобработки;
* завершение классификации;
* расчёт метрик;
* формирование рекомендации;
* запросы к Ollama/Gemma;
* успешные ответы Gemma;
* ошибки соединения и timeout;
* CSV-экспорт;
* непредвиденные исключения.

В логи не записываются:

* полные транскрипты;
* номера телефонов;
* чувствительные данные;
* ключи и секреты.

Папка `logs` создаётся автоматически.

## Ограничения текущего анализа

Основная классификация основана на прозрачных rule-based правилах.

Это обеспечивает:

* быстрый запуск;
* отсутствие внешних API-зависимостей;
* воспроизводимость;
* проверяемость логики.

Ограничения:

* нестандартные формулировки клиента могут быть распознаны неточно;
* сарказм и сложный контекст не анализируются полноценно;
* часть смысловых ответов может не попасть в нужный этап;
* качество классификации зависит от словарей и правил;
* отсутствие транскрипта не позволяет определить содержание звонка.

LLM-анализ может быть следующим улучшением для смысловой классификации нестандартных ответов, но он не является обязательным для работы текущего продукта.

## Основная продуктовая позиция

Дашборд не оптимизирует сырое количество встреч.

Главная цель — увеличить количество осмысленных следующих шагов с потенциально релевантными клиентами.

Поэтому основная метрика:

```text
Qualified Next Step Rate
```

Продукт помогает аналитику перейти от сырой выгрузки к решению:

```text
где теряется клиент
→ почему это важно
→ какая метрика это доказывает
→ какие звонки проверить
→ какой A/B-тест запустить первым
```
